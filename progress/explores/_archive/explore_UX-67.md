# Reporte de Exploracion - UX-67 (Edicion de productos usados y notas en el historial de visitas)

**Pregunta:** Diseno concreto (backend + frontend) para permitir editar `notes` y `productsUsed` de un `ServiceRecord` ya registrado, con reconciliacion de stock por delta, sin dejar cambios parciales ante fallo de validacion.
**Contexto:** UX-67, `feature_list.json` (in_progress). Backend: `apps/server/src/controllers/serviceRecordController.ts` `updateServiceRecord`. Frontend: `apps/client/src/views/Historial.tsx` + patron de `apps/client/src/components/RegistroModal.tsx`.
**Timestamp:** 2026-07-31

## Diagnostico

El backend actual excluye productsUsed del whitelist de edicion precisamente porque nadie implemento la reconciliacion de stock; agregarla requiere leer el registro viejo ANTES de mutar nada (hoy updateServiceRecord no hace ese fetch), calcular deltas producto por producto contra el estado nuevo del body, y separar estrictamente una fase de validacion de solo lectura (todo el union de productos, comprobar pertenencia al tenant y suficiencia de stock) de una fase de escritura (aplicar los deltas y recien despues actualizar el ServiceRecord), replicando el mismo principio de orden como mitigacion de atomicidad que ya usa createServiceRecord/P6. En rutas falta agregar los validators de productsUsed al PUT (ya existen para el POST, es un mirror literal). En frontend no existe todavia ningun patron de editar productsUsed de un registro ya creado - hay que construir un nuevo modal (no extender RegistroModal.tsx, que trae campos irrelevantes para edicion como client/service/professional) reusando exclusivamente el bloque de selector de insumos + useFieldArray, con especial cuidado en mapear product poblado a _id string al prefillear.

## Recomendacion

Implementar la reconciliacion en updateServiceRecord con el algoritmo exacto detallado abajo y crear un componente nuevo EditRegistroModal.tsx (o nombre equivalente) enfocado solo en notes + productsUsed, en vez de extender RegistroModal.tsx.

### Algoritmo de reconciliacion de stock por delta (backend)

**Paso 0 - Fetch previo (nuevo, no existe hoy):**
```typescript
const existingRecord = await ServiceRecord.findOne({ _id: id, tenantId: req.tenantId });
if (!existingRecord) {
    return res.status(404).json({ error: 'Registro no encontrado' });
}
```
Este fetch reemplaza la actual estrategia de "solo findOneAndUpdate" y es lo que garantiza el 404 ANTES de tocar cualquier stock (evita el escenario de aplicar deltas y luego descubrir que el registro no existe/no es del tenant).

**Paso 1 - Whitelist + validacion de fecha:** igual que hoy (lineas 231-243), sin cambios.

**Paso 2 - Reconciliacion (solo si req.body.productsUsed !== undefined; OJO: undefined = "no tocar", array vacio [] = "vaciar todos los productos y restaurar todo el stock" - son casos distintos, no usar el chequeo `productsUsed && Array.isArray(...) && length > 0` de createServiceRecord, que trataria [] como "no hacer nada"):**

1. Rechazar duplicados dentro del nuevo array: si body.productsUsed tiene el mismo product id repetido, responder 400 con error 'Producto duplicado en la lista de insumos' (falla temprano, sin leer stock). Mirror del guard que ya hace RegistroModal.tsx en el cliente (fields.some(...)), pero el backend nunca debe confiar en que el frontend lo evito.
2. Construir oldMap: Map<string, number> desde existingRecord.productsUsed (item.product.toString() a item.quantity).
3. Construir newMap: Map<string, number> desde body.productsUsed (ya sin duplicados).
4. unionIds = [...new Set([...oldMap.keys(), ...newMap.keys()])].
5. Un solo query: const products = await Product.find({ _id: { $in: unionIds }, tenantId: req.tenantId }). Si products.length !== unionIds.length, algun id no pertenece al tenant o no existe, responder 400 con error 'Uno o mas insumos no son validos para este negocio' (anti-IDOR, SEC-B). No filtrar por isActive (consistencia con el resto de lookups de stock).
6. Para cada id en unionIds: delta = (newMap.get(id) ?? 0) - (oldMap.get(id) ?? 0). Si delta > 0 (se necesita consumir mas stock del que ya se habia descontado): comprobar product.stock >= delta; si no, responder 400 con mensaje descriptivo de stock insuficiente y RETORNAR INMEDIATAMENTE sin haber mutado nada todavia (este loop es 100% de lectura).
7. Solo si el loop completo de validacion paso sin retornar 400: recien ahi aplicar mutaciones, iterando otra vez sobre unionIds con delta !== 0: product.stock -= delta; await product.save(); (la misma formula sirve para ambos signos: delta positivo resta, delta negativo -producto restaurado- suma).
8. updateData.productsUsed = body.productsUsed (normalizado a { product, quantity }[], nunca objetos poblados).

**Paso 3 - Update final:** igual que hoy, ServiceRecord.findOneAndUpdate({ _id: id, tenantId: req.tenantId }, { $set: updateData }, { new: true, runValidators: true }).

**Rutas - agregar al PUT en apps/server/src/routes/serviceRecordRoutes.ts (mirror literal del POST, lineas 70-74):**
```typescript
body('productsUsed').optional().isArray().withMessage('productsUsed debe ser una lista (array)'),
body('productsUsed.*.product').isMongoId().withMessage('Cada producto usado debe tener un ID valido'),
body('productsUsed.*.quantity').isNumeric().withMessage('La cantidad debe ser un numero').custom(value => value > 0).withMessage('La cantidad debe ser mayor a 0'),
```

## Riesgos / edge cases

1. **Producto duplicado en el nuevo productsUsed:** el backend debe rechazarlo explicitamente con 400 (no sumarlo silenciosamente ni quedarse con el ultimo) - sin este guard, newMap colapsaria entradas duplicadas de forma ambigua segun el orden de insercion del Map, ocultando un error de payload en vez de reportarlo.
2. **Producto agregado que no estaba en el registro original:** oldMap.get(id) ?? 0 cubre el caso naturalmente (delta = newQty), pero requiere que el producto exista y pertenezca al tenant (paso de validacion por $in); si no, 400 IDOR-safe (no 404, porque no es un lookup por :id de ruta sino una referencia embebida en el body - usar 400 como en createServiceRecord, no 404).
3. **Stock insuficiente a mitad de la reconciliacion:** mitigado por el diseno de dos fases (validar TODO el unionIds antes de mutar ninguno) - si se aplicara producto por producto sin esta separacion, un fallo en el tercer producto dejaria los dos primeros ya descontados sin rollback (no hay session.withTransaction disponible en este stack, ver docs/patterns-backend.md P6 nota de atomicidad).
4. **Condicion de carrera con otra visita concurrente (TOCTOU):** el diseno de dos fases resuelve el "todo o nada" DENTRO de un mismo request, pero NO resuelve dos requests concurrentes que ambos leen el mismo product.stock antes de que cualquiera escriba (ej. dos ediciones simultaneas del mismo producto, o una edicion concurrente con una creacion nueva que consume el mismo insumo): ambos pueden pasar la validacion de suficiencia leyendo el mismo valor stale y luego ambos .save() decrementar, dejando stock potencialmente negativo hasta que el validador Mongoose min:0 lo bloquee en el segundo .save() - que lanzara una excepcion de validacion capturada por el catch generico y devuelta como 500 (no como 400 descriptivo), perdiendo la semantica de "stock insuficiente". Mitigacion recomendada (no implementada en el patron actual, evaluar con el implementer/reviewer si corresponde a esta feature o a un hardening posterior): para el caso de decremento (delta > 0) usar Product.findOneAndUpdate({ _id, tenantId, stock: { $gte: delta } }, { $inc: { stock: -delta } }) atomico en vez de read-check-save(), tratando null como resultado como stock insuficiente. Para incrementos (restauracion, delta < 0) no hay riesgo de negativo, un $inc simple es seguro sin necesidad de guard.
5. **productsUsed: [] explicito (vaciar todos los insumos) vs. campo omitido:** deben tratarse distinto - undefined no reconcilia nada (comportamiento actual preservado para clientes que solo editan notes); [] es una reconciliacion valida que restaura el 100% del stock consumido originalmente. Usar req.body.productsUsed !== undefined como guard de entrada al bloque de reconciliacion, no un chequeo de longitud/truthiness.
6. **Producto viejo ya no existe / fue soft-deleted (isActive: false) al momento de editar:** el Product.find({ _id: { $in }, tenantId }) sin filtro isActive si lo encuentra (mismo comportamiento que createServiceRecord), asi que restaurar/ajustar stock de un producto desactivado sigue funcionando - pero si el producto pertenece a otro tenant, cae en el 400 de "insumo invalido", lo cual bloquearia incluso una edicion que solo quiere cambiar notes sin tocar productos - mitigado porque el bloque de reconciliacion solo corre si productsUsed !== undefined en el body (si el frontend no reenvia productsUsed cuando no se toco, este edge case no se dispara).
7. **quantity fraccionaria o con muchos decimales:** el validator existente solo exige isNumeric() + > 0, sin restriccion de enteros; mismo comportamiento heredado del POST, no es una regresion nueva de esta feature pero vale mencionarlo si el reviewer pregunta por que no se valido isInt.
